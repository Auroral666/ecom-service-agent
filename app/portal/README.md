# 账号与人工服务

账号、权限和人工服务集中在本目录，复用原有聊天和 SSE 接口。没有调整 Agent、ReAct、工具或 RAG 实现。

## 角色与首次使用

打开前端，选择用户、客服或开发人员身份后注册/登录。用户进入 `/chat`，客服进入 `/support`，开发人员进入 `/dev`。右上角显示名称、文字头像及退出菜单。

用户可直接注册。客服和 dev 注册需要对应邀请码。首次启动后自动生成在 `app/sessions/web/.portal/invitations.json`，由本机项目负责人读取并提供；不通过网页接口返回，不设固定默认密码。邀请码可重复用于创建本地演示员工账号；不要公开该文件。

账号和会话凭据存储在同目录 `portal.sqlite3`。密码使用带随机盐的 scrypt，登录凭据仅以摘要存储，浏览器使用 12 小时 HttpOnly、SameSite=Strict Cookie；HTTPS 请求会附加 Secure。退出会撤销当前登录凭据。修改身份选择或前端 URL 不会改变后端角色。

需要同时演示用户和客服时，使用两个浏览器或一个普通窗口加一个隐私窗口。相同浏览器配置的多个标签共用登录 Cookie，会同步账号切换。

## 人工服务

用户保留多个自动客服会话，但人工通道按用户 ID 唯一。转人工后进入等待状态，后续消息（含新建会话中的消息）都发到人工通道，不调用 Agent。客服接入后可回复，其他客服不能抢占或结束该服务。结束后恢复自动客服，历史记录保留。

每次转人工创建独立人工服务记录，名称为“用户ID-用户显示名-北京时间启动时间戳”（如 `用户ID-小明-20261101T113015123`），名称创建后固定。客服接入后可先发消息；双方消息均关联当前服务 ID，不再根据旧轮次的客户消息决定回复归属。

客服端按用户汇总全部咨询历史，也可通过“人工服务记录”选择框单独查看某轮服务。用户端在人工服务期间切换咨询窗口仍可看到当前轮次的全部消息，结束后可在发起转人工的咨询窗口查看完整记录。重开服务创建新记录并递增版本号，防止旧页面误操作。首次启动自动迁移旧消息，按转人工通知划分历史轮次，保留原消息及来源会话。

双方通过短轮询同步人工消息（用户 1.5 秒，客服 2 秒）。原有自动回复继续使用真正的 SSE。人工状态和消息重启后仍保留。删除/清空自动客服记录前会归档，保证客服历史连续。

## 权限与旧记录

会话归属在服务端校验，普通用户只能读取自己的会话；只有 dev 能调用调试接口，原有本机访问限制和临时调试令牌仍生效。原来的无账号演示会话只给 dev 展示，不分配给新用户。

构造 Agent 后、首轮调用前，会替换为当前账号的长期记忆文件，避免沿用原来的 default 用户长期记忆。原有工具全局引用仍靠 ChatService 的锁串行切换，不移除该锁。

现有订单、物流等工具仍使用项目原有 Mock 业务数据；本次账号系统没有把这些演示数据改造成真实订单的多租户权限系统。人工消息单独存储，不写入 Agent 的内部上下文。

## 接入点与验证

- `store.py`：SQLite 持久化、账号和人工服务状态。
- `routes.py`：登录、注册、人工服务接口和角色/会话权限中间件。
- 原 `app/api/main.py`：注册模块、过滤/绑定会话归属、删除前归档。
- 原 `app/api/service.py`：调用前人工状态检查及账号记忆准备钩子。
- 前端 `src/portal/`：登录注册、客服工作台、用户菜单、状态/API/样式；原聊天页面移至 `ChatWorkspace.vue` 保留。

隔离后端验证：`python -B -X utf8 -m pytest -q tests/test_portal.py tests/test_web_api.py tests/test_streaming.py tests/test_first_token.py tests/test_embedding_configuration.py --basetemp=frontend/.ui-review/pytest-portal-new-run`。每次选择新的 basetemp。浏览器验证使用真实隔离账号/人工服务 API 和模拟 Agent，报告在 `frontend/.ui-review/portal-browser.json`，不创建正式账号。
